# Хранилище ключ-значение — практика 14

Продолжение проекта тринадцатой практики. Показатели базы выражены через
фильтрацию, преобразование и свёртку. Главное новое — доля мусора
в журнале. Команда `summary` печатает сводку, а `stats` теперь тоже
показывает долю мусора. Всё, что умела программа на практике 13,
осталось.

## Что сделано

**Три операции над парами любого движка** (`src/store_stats.hpp`). Все
построены на обходе `for_each` из практики 13:

| Операция | Функция |
|---|---|
| filter | `select_keys(engine, predicate)` — ключи подходящих пар |
| map | `map_pairs(engine, value)` — число для каждой пары |
| reduce | `reduce_pairs(engine, initial, step)` — свёртка с начальным значением |

Итераторов движок не даёт, поэтому `reduce_pairs` — свой аналог
`std::accumulate` поверх обхода. Накопитель живёт только в нём,
а показатели передают шаг.

**Показатели:**

| Показатель | Как выражен |
|---|---|
| Число живых ключей | `reduce_pairs` с шагом «плюс один» |
| Суммарный размер ключей и значений | `map_pairs` в размеры, `std::accumulate` с `0LL` |
| Средний размер значения | `map_pairs`, сумма свёрткой, деление в `double`; пустая база — 0 |
| Наибольший размер значения | `reduce_pairs` с `std::max`, начальное значение 0 |
| Ключи по первому символу | `map_pairs` в первый символ, группировка словарём `std::map` |

Для наибольшего размера 0 — верное начальное значение: размер не бывает
отрицательным, и 0 — наименьший возможный.

**Доля мусора** — `JournalEngine::garbage`. Проходит по всем записям
журнала: `JournalFile::records()` перечитывает файл и возвращает позицию
записи на место.

1. map: размер каждой записи в байтах. Сумма свёрткой — это весь файл.
2. Группировка: номер последней записи каждого ключа, словарём
   по номерам записей.
3. filter и reduce: складываются размеры только актуальных записей.
   Актуальна последняя запись своего ключа, если это `put`.

Надгробие — тоже последняя запись своего ключа, но актуальным оно
не считается: пары больше нет, а место занято. Мусор — всё остальное,
в процентах и байтах. Пустой журнал даёт 0 %, а не деление на ноль.

**Где показан мусор.** Долю мусора печатает `describe()` журнального
движка, поэтому она появилась и в `summary`, и в `stats`. У движка
в памяти журнала нет, и о мусоре он ничего не пишет.

## Почему доля мусора — главный показатель

Журнал только растёт. Каждая перезапись и каждое удаление добавляют
запись и не освобождают ни байта. База, где каждый ключ перезаписан
трижды, на две трети состоит из мусора. Все остальные показатели
описывают данные, а этот — цену их хранения. Он показывает, сколько
лишнего читается при каждом открытии и сколько места занято зря.
Во втором семестре по нему будет запускаться уплотнение: когда доля
мусора переходит порог, журнал переписывается заново, только из
актуальных записей. Порог выбирается так, чтобы уплотнение не шло
слишком часто — оно само переписывает весь файл — и чтобы мусор
не успевал разрастись.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build
./build/key_value_sore -f tri.db
> put a 1
> put a 2
> put a 3
> summary
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

## Проверка

База, где 100 ключей перезаписаны трижды:

```
Journal records: 300, obsolete among them: 200
Garbage in the journal: 66.7% (3568 of 5352 bytes)
```

5352 байта — ровно размер файла. После двух `del` мусора 67,4 %:
удалённые пары и их надгробия ушли в мусор. На пустой базе средний размер 0,0
и мусора 0,0 %. После `summary` новые `put` ложатся в конец журнала
и читаются при следующем открытии. Значит, `records()` вернул позицию
на место.

Сценарий из тридцати команд практики 13 дал тот же вывод, кроме новой
строки о мусоре в ответах `stats`. Журналы совпадают байт в байт. `ctest`
и `conform` проходят на обоих движках. Всё прогнано под санитайзерами
адресов, неопределённого поведения и утечек — без ошибок.

## На что обратить внимание при разборе

**Актуальность — по последней записи ключа, не по смещению из индекса.**
Таблица в памяти знает только живые значения. Удалённого ключа в ней
нет вовсе, поэтому надгробие по ней не распознать как мусор.

**Начальное значение свёртки.** Суммы — с `0LL`: размеры файлов в `int`
не всегда помещаются. Наибольший размер — с 0, потому что размеры
неотрицательны. Для яркости или времени так было бы нельзя.

**Деление на ноль.** Средний размер на пустой базе — 0, доля мусора
пустого журнала — 0 %. Обе проверки стоят до деления.

**Условие без побочных эффектов.** Предикат `select_keys` только отвечает.
Если бы он менял хранилище, обход сломался бы (практика 13).

**Константный метод, который читает файл.** `records()` двигает позицию
в файле, но возвращает её на место и самих данных не меняет. Поэтому
`describe` остаётся `const`.
