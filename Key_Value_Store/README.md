# Хранилище ключ-значение — практика 11

Продолжение проекта десятой практики. У библиотеки появился публичный
заголовок, который не раскрывает ничего из внутреннего устройства.
Демонстрационные программы видят только его. Инвариант хранилища записан.
Вся работа с файлом журнала — в отдельном классе. Всё, что умела программа
на практике 10, осталось.

## Что сделано

**Публичный заголовок `include/kvstore.hpp`.** В нём только то, что видит
клиент: `KvStatus`, `status_text`, `KvError` и класс `KvStore`. Нет ни
хеш-таблицы, ни формата записей, ни смещений, ни слова «журнал». Каждая
операция обоснована в комментарии к классу:

| Операция | Зачем клиенту |
|---|---|
| `KvStore(path)` | открыть базу: без этого не с чем работать |
| `put` | сохранить или заменить значение |
| `get` | прочитать значение |
| `remove` | удалить пару |
| `size` | число пар, не копируя их |
| `pairs` | все пары: показать справочник целиком |
| `repaired` | сказать пользователю, что после сбоя часть данных потеряна |

Чего в интерфейсе нет: счётчиков журнала, закрытия (его делает деструктор),
копирования.

**Устройство спрятано за указателем.** `KvStore` хранит
`std::unique_ptr<Store>`, а в заголовке `Store` только объявлен. Тот же
приём, что неполный тип в публичном заголовке версии на C. Поэтому
`kvstore.hpp` не включает ни `store.hpp`, ни `unordered_map`, ни
`journal_file.hpp`: сменятся внутренности — клиентов перекомпилировать
не придётся.

**Граница проведена в CMake.** Каталог `../../Users/Никита/Downloads/kvstore/include` у библиотеки публичный,
`src/` — закрытый. Справочник и счётчик получают только `include/`, и
`#include "store.hpp"` в них просто не соберётся. Консоль — инструмент
самой библиотеки: ей нужны подробности журнала (`stats`, `record`),
поэтому ей открыт и `src/`.

**Демонстрационные программы.**

- Телефонный справочник переведён на `KvStore`. Строку о записях журнала
  он больше не печатает: это подробность устройства.
- Новая программа `visits` — счётчик посещений страниц. Она написана
  только по публичному заголовку. Отдельной операции «значение или ноль»
  ей не понадобилось: хватило `get` и ответа `not_found`.

**Инвариант хранилища** (`include/store.hpp`) — связь таблицы с журналом:

- таблица — ровно то, что получится, если применить все целые записи
  журнала по порядку;
- `записей в журнале == ключей + ненужных записей`.

Держится он порядком действий: сначала журнал, потом таблица. Записаны
и инварианты `KvStore`, `JournalFile`, `Session` и `Record`.

**Журнал отдельно.** На практике 10 хранилище само перечитывало журнал
по записям, решало, когда отрезать хвост, и кодировало запись в байты.
Теперь у `JournalFile` два открытых действия: `recover(records)` отдаёт
все целые записи и сам отрезает хвост, `append(record)` дописывает одну.
Шаги чтения стали закрытыми. В `Store` не осталось ни байтов, ни позиций
в файле.

**`trace` закрыт.** `Store::trace` и `JournalFile::trace` были открытыми
статическими полями, теперь их меняет `set_trace`.

**Опыт 5 в `demo`.** Пробует нарушить инвариант через публичный интерфейс
и проверяет равенство после повторного открытия.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build                       # kvlib, kvstore, phonebook, visits
./build/kvstore put name "Ivan Petrov"
./build/kvstore                           # интерактивный режим
> demo
./build/phonebook book.db add Ivan +7-900-111-22-33
./build/phonebook book.db list
./build/visits site.db main               # засчитать посещение
./build/visits site.db                    # все страницы
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

## На что обратить внимание при разборе

**Второй клиент — самая полезная часть.** Пока клиент один, любой интерфейс
кажется удобным: он ровно под этого клиента и сделан. Справочнику
на практике 10 зачем-то были нужны счётчики журнала. Счётчику посещений
они не нужны — значит, это не часть договора с клиентом.

**Инвариант связывает две вещи.** «Поля правильные» — не инвариант.
«Таблица — результат применения журнала» — инвариант: им объясняется,
почему `apply` пишет в журнал раньше, чем в таблицу.

**Ссылка на индекс отменяет защиту.** Отдай `Store` ссылку на
`unordered_map`, и клиент мог бы очистить её. Журнал на диске остался бы
прежним, а при следующем открытии все пары вернулись бы.

**Включение ради одного типа.** Если бы `kvstore.hpp` включал `store.hpp`
ради `Store`, клиент перекомпилировался бы при каждом изменении внутренностей.
Объявления `class Store;` хватает, чтобы хранить указатель.

**Деструктор `KvStore` определён в `.cpp`.** `unique_ptr` удаляет объект,
а удалить неполный тип нельзя. В заголовке `Store` неполный, в
`kvstore.cpp` — полный, поэтому деструктор и перемещения определены там:
`= default`, но в нужном месте.

**Объект после перемещения.** Пустой `KvStore` жив, и его операции отвечают
`bad_argument`, а не обращаются к чужой базе.
