# Хранилище ключ-значение — практика 12

Продолжение проекта одиннадцатой практики. Способ хранения стал сменяемым.
Абстрактный движок `Engine` и два наследника: журнальный и в памяти.
Консоль, справочник и счётчик посещений работают с любым движком, не зная
его типа. Выбор движка — в одном месте. Один и тот же набор проверок
проходит на обоих движках. Всё, что умела программа на практике 11,
осталось.

## Что сделано

```
Engine (абстрактный: put, get, remove, pairs, size, repaired, describe)
├── JournalEngine   таблица в памяти и журнал на диске — бывший Store
└── MemoryEngine    только таблица в памяти
```

**Интерфейс движка.** Четыре операции: положить, получить, удалить, обойти
(`pairs`). К ним `size`, `repaired` — повреждены ли были данные при
открытии — и `describe`: подробности устройства, которые каждый движок
описывает сам.

- Деструктор виртуальный, копирование через базу запрещено, конструкторы
  и перемещение защищённые.
- Проверка длин ключа и значения одна на всех — `Engine::valid_pair`.

**Выбор движка в одном месте.** Его делает `make_engine(имя)`: имя
`:memory:` (`KvStore::IN_MEMORY`) — движок в памяти, любое другое — журнал
с этим файлом. Больше нигде в программе вид движка не упоминается.

**Клиенты.**

- `KvStore` (публичный заголовок) хранит `std::unique_ptr<Engine>`.
  Справочник и счётчик посещений не изменились ни на строку, а работают
  и с базой в памяти: `phonebook :memory: add ...`.
- Сессия консоли хранит два `std::unique_ptr<Engine>`. Закрытое
  хранилище — пустой указатель.
- `./kvstore -f :memory:` — первое хранилище в памяти. `open :memory:`
  открывает базу в памяти на месте текущей.
- `Record::apply_to` и `SortedPairs::build` принимают `Engine&`.

**Где виден журнал.** Журнальные подробности остались только в журнальном
движке. Команда `stats` печатает `describe()` движка: у журнального — те же
строки о записях журнала, что раньше, у движка в памяти — одну строку
о том, что на диск ничего не пишется. Консоль не спрашивает, какой перед
ней движок.

**Общий набор проверок** — `run_conformance(Engine&)`, 17 проверок через
один интерфейс: пустой новый движок, замена значения, `not_found`, длины
на границе и за ней, пустое значение, любые байты, обход, 1000 пар.

- Команда `conform` прогоняет его на обоих движках.
- Программа `engine_tests` делает то же для `ctest` и добавляет одну
  проверку только журнальному движку — сохранность после повторного
  открытия.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build                  # kvlib, kvstore, phonebook, visits, engine_tests
ctest --test-dir build               # общий набор на обоих движках
./build/kvstore                      # журналы store1.db и store2.db
./build/kvstore -f :memory:          # первое хранилище — в памяти
> conform
./build/phonebook :memory: add Ivan 1
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

## Проверка

`conform` и `ctest`: на движке в памяти и на журнальном все 17 проверок
`ok`, у журнального сохранность после повторного открытия тоже `ok`.

С `-f :memory:` всё работает как с журналом: `put`, `list`, `copy`
в журнальное второе хранилище, `close`, `open store1.db`. `stats` у базы
в памяти — `Engine: in memory only, nothing is written to disk`.

Сценарий из пятидесяти команд практики 11 дал тот же вывод, кроме слов
в сообщениях `use`, `which`, `open` и `close`. Там, где говорилось
«journal», теперь «database», а из `close` ушло «Journal ... stays
on disk»: у базы в памяти нет журнала. Журналы совпадают байт в байт. Всё
прогнано под санитайзерами адресов, неопределённого поведения и утечек —
без ошибок.

## На что обратить внимание при разборе

**Набор проверок — принцип подстановки в деле.** Любой наследник `Engine`
должен проходить один и тот же набор: он годится везде, где ждут `Engine`.
Если один движок проходит, а другой нет, то либо в нём ошибка, либо
интерфейс обещает лишнее.

**Чего интерфейс не обещает.** Сохранности после перезапуска. Движок
в памяти честно её не даёт, поэтому этой проверки в общем наборе нет —
она отдельно и только у журнального. Это подводка к практике 26.

**Метод, осмысленный для одной реализации, — запах.** Число записей
журнала и ненужных записей есть только у журнала. В `Engine` их нет:
вместо этого `describe`, который каждый движок заполняет по-своему.

**Виртуальный деструктор.** Без `virtual` у `~Engine` удаление через
`unique_ptr<Engine>` не вызвало бы `~JournalEngine`. Журнал не закрылся бы,
а буфер не сбросился бы на диск.

**Срезка.** Копирование `Engine` запрещено. Копия через базовый класс
получила бы только часть `Engine` — без таблицы и журнала. А копия
журнального движка писала бы в тот же файл.

**Защищённое перемещение.** Если в базе удалить копирование и ничего
не сказать о перемещении, у наследника пропадёт и перемещение. Поэтому
в `Engine` оно объявлено `protected` и `= default`: опыт 4 в `demo`
по-прежнему перемещает журнальный движок.

**Один выбор — одно место.** Проверки «если :memory:» в консоли,
в `KvStore` и в справочнике не нужны: всё решает `make_engine`.
