# Растровый редактор — практика 8

Продолжение проекта седьмой практики: общее перечисление кодов ошибок,
структура цвета и двоичная разновидность формата PPM.

## Что сделано

- Модуль `status`: общее перечисление кодов ошибок `ImgStatus` и функция
  перевода кода в сообщение. На него переведены все функции, способные
  не справиться: создание, копия, обрезка, масштаб, поворот, минимум
  и максимум, чтение и запись файла.
- Цвет описан структурой `Color`, заливка получает её по адресу.
- `ppm` читает и пишет обе разновидности: текстовую P3 и двоичную P6.
  Какая перед нами, определяется по сигнатуре.
- `save <файл> [text|bin]` выбирает разновидность, `load` сообщает, что прочитал.
- Всё из практик 1–7 работает как прежде.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build
./build/raster
> size 800 600
> gen gradient
> save g.ppm bin
> load g.ppm
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

## Проверка

Изображение 4000 на 3000, сборка `-DCMAKE_BUILD_TYPE=Release`:
текстовый файл 128 МБ читается 1,39 с, двоичный 36 МБ — 0,24 с.
Двоичный файл меньше в 3,6 раза и читается в пять с лишним раз быстрее.
Байты данных P6 совпадают с числами P3 того же изображения. Оборванный
двоичный файл даёт понятную ошибку и не портит открытое изображение.
Под адресным санитайзером, который ищет и утечки, чисто.

### Ошибки

| Файл или команда | Ответ |
|---|---|
| P6, оборванный на середине данных | `corrupted data` |
| P3 со значением 999 при максимуме 255 | `corrupted data` |
| Сигнатура P5 | `invalid format` |
| Ширина 99999999999 | `invalid format` |
| P6 с максимумом 65535 (два байта на канал) | `invalid format`, такие файлы не поддерживаются |
| Отсутствующий файл | `cannot open the file` |
| `save` в несуществующий каталог | `cannot open the file` |
| Ошибка записи у открытого файла (кончилось место) | `write failed` |
| `crop 2147483647 0 10 10` | прямоугольник вне изображения, без переполнения |

## На что обратить внимание при разборе

**Один пробельный символ после заголовка.** В двоичном файле за максимумом
канала идёт ровно один пробельный символ, а дальше сразу байты. Пропускать
пробелы дальше нельзя: первый байт данных может по значению совпасть
с кодом пробела, и тогда картинка сдвинется на пиксель. Это самая частая
ошибка при чтении P6, и найти её тяжело — изображение выглядит почти верным.

**Двоичный режим открытия.** Для P6 он обязателен. В текстовом режиме
на части систем байты, совпадающие с кодом перевода строки, молча
подменяются, и каждый такой пиксель портится.

**Один набор кодов на весь проект.** До этой практики у модуля `ppm` были
свои коды, а у операций над изображением — просто 0 и 1. Теперь `status.h`
заводит `ImgStatus` с шестью кодами из задания и седьмым — ошибкой записи:
место на диске может кончиться у уже открытого файла, и это не «файл
не открылся». Вызывающий проверяет результат одинаково везде и печатает
одно и то же сообщение для одной и той же беды.

**Структура вместо трёх параметров.** Цвет, который передают и разбирают,
описан структурой `Color`: `fill_region` получает её адрес вместо трёх
каналов. Сам пиксель по-прежнему хранится упакованным в одно число —
так изображение занимает меньше памяти. Маленькая структура из трёх байтов
возвращается по значению: `pixel_to_color`.

**Ни один результат записи не игнорируется.** `ppm_save` проверяет каждый
`fprintf`, `fwrite`, `fputc` и результат `fclose`: часть ошибок записи
видна только при закрытии, когда буфер уходит на диск. Чтение и запись
разложены по функциям, которые просто возвращают код, а файл закрывается
в одном месте.

**Почему файл меньше втрое.** В текстовом виде число занимает от двух
до четырёх символов плюс разделитель, в двоичном — ровно один байт.

**Разновидность определяется по файлу, а не по расширению.** Имя файла
ничего не гарантирует, сигнатура гарантирует.
