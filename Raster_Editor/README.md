# Растровый редактор — практика 11

Продолжение проекта десятой практики. Все поля закрыты, инварианты записаны,
цвет насыщает каналы на входе, работа с файлами PPM вынесена из изображения
в отдельный класс. Всё, что умел редактор на практике 10, осталось.

## Что сделано

Инварианты записаны комментарием над каждым классом:

| Класс | Инвариант |
|---|---|
| `Color` | каждый канал в пределах 0..255; число вне пределов насыщается, а не обрезается по модулю |
| `Image` | пустое 0 на 0 без буфера, либо обе стороны от 1 до 8192 и буфер ровно `ширина * высота` цветов |
| `Editor` | изображение пустое или верное по инварианту `Image`; своих проверок нет, всё через открытые методы |
| `PpmFile` | состояния нет — нет и инварианта |

Как методы поддерживают инварианты:

- **Каналы цвета насыщаются.** `Color::from_rgb` принимает `int` и насыщает
  каждый канал сам. На практике 10 параметры были `std::uint8_t`,
  и `from_rgb(300, 0, 0)` давал канал 44: число обрезалось ещё при вызове,
  до проверки. Теперь получается 255.
- **Доступ по координатам проверяет границы.** `pixel` за пределами
  возвращает чёрный, `set_pixel` ничего не пишет и возвращает `false`.
- **Размер меняется вместе с буфером.** Обрезка, поворот, масштаб
  и чтение строят новый объект и перемещают его на место старого. Ошибка
  оставляет изображение прежним.
- **Указателя на буфер наружу нет.**
- **`trace` закрыт.** `Image::trace` было открытым статическим полем,
  теперь его меняет `Image::set_trace`.

Чтение и запись PPM перенесены в класс `PpmFile`:
`PpmFile::read(path, image, format)` и `PpmFile::write(path, image, format)`.
Он пользуется только открытыми методами изображения: конструктором,
`set_pixel`, `pixel`, размерами. В классе `Image` не осталось ни одного
потока и ни одного имени файла.

Перечисление `ImageStatus` и функция `status_text` переехали в свой
заголовок `status.hpp`: ими отвечают и изображение, и файлы.

`demo` получил опыт 7: попытки нарушить инварианты снаружи. `colors`
печатает в конце, во что `from_rgb` превращает каналы 300, -20 и 128.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build
./build/raster
> demo
> size 800 600
> gen gradient
> save g.ppm bin
./build/raster checker.ppm gen checker 16
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

```
  set_pixel(10, 10): rejected, outside
  pixel(-1, 0): 0 0 0 - black, nothing read outside the buffer
  channels 999 -5 128 stored as 255 0 128
  crop past the edge: invalid argument, size still 4 x 3
  scale to 100000 x 2: too large: at most 8192 x 8192, size still 4 x 3

```

Сценарий из сорока команд дал тот же вывод, что практика 10, кроме новой
строки в `colors`. Файлы, записанные обеими версиями, совпадают байт в байт.
Оборванные P3 и P6, файл P5, слишком большой размер, значение больше
максимума и файл с комментарием и максимумом 100 читаются с теми же
ответами, что на практике 10. Всё прогнано под санитайзерами адресов,
неопределённого поведения и утечек — без ошибок.

## На что обратить внимание при разборе

**Инвариант — равенство, а не «поля правильные».** Для изображения это
`буфер == ширина * высота` и границы сторон. Его можно проверить одной
строкой в любой момент.

**Тип поля держит инвариант не до конца.** `std::uint8_t` не вмещает 300,
но и не насыщает: 300 молча становится 44. Поэтому проверка должна стоять
там, где число попадает в объект, и до того, как оно сузится.

**Указатель на буфер отменяет всю защиту.** Метод, отдающий `Color*`,
позволил бы писать за концом блока и хранить указатель после того, как
`crop` освободил буфер. `set_pixel` с проверкой стал бы бесполезен.

**Действие, а не поле.** Изображению не нужны `set_width` и `set_height`:
снаружи нужны действия — обрезать, повернуть, изменить размер. Каждое меняет
размеры и буфер вместе.

**Почему файлы отдельно.** Добавится третий формат — изменится `PpmFile`
или появится соседний класс, а `Image` останется прежним. У каждого класса
одна причина меняться.

**Отдельный класс работает через открытые методы.** `PpmFile` не `friend`
изображения. Испорченный файл не может нарушить инвариант изображения:
все пиксели проходят через `set_pixel`.

**Статические методы.** У `PpmFile` нет полей, поэтому создавать его объект
незачем. Закрытые статические методы `read_header` и `read_pixels` — шаги
разбора, которые снаружи никому не нужны.

## Язык вывода

Всё, что программа печатает, — на английском: сообщения, подсказки, справка.
Комментарии в коде — на русском. Так вывод читается в любой консоли,
в том числе в консоли Windows, где кириллица в UTF-8 без настройки
превращается в нечитаемые символы.
