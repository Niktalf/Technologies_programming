# Анализатор логов — практика 4

Продолжение проекта третьей практики: сортировка слиянием и двоичный поиск.

## Что сделано

- Модуль `sort`: рекурсивная сортировка записей по времени слиянием
  и рекурсивный двоичный поиск первой записи не раньше заданного момента.
- Новые команды: `sort` и `since <ГГГГ-ММ-ДД> <чч:мм:сс>`. Если журнал
  не отсортирован, `since` сортирует его сама и сообщает об этом.
- Каждая команда — отдельная функция; цикл `shell_run` только выбирает команду.
- Всё из практик 1–3 работает как прежде, фильтр уровней действует
  на `head`, `tail` и `count`.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build
./build/logan
> gen test.log 12000 7
> load test.log
> since 2026-03-15 12:00:00
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

## Проверка

```
> since 2026-03-15 12:00:00
The log is not sorted, sorting.
Records sorted: 10000, max recursion depth: 15
First matching record - number 5181 of 10000:
2026-03-15 12:01:08  DEBUG  disk      connection established #777
2026-03-15 12:07:34  INFO   cache     timeout exceeded #7201
...
```

Результаты поиска сверены с двоичным поиском Python (`bisect_left`) на пяти
моментах: до всех записей, после всех, середина, точное совпадение, последняя
запись. Отдельно проверен момент, встречающийся в журнале дважды: находится
первая из двух записей, и они идут в исходном порядке — сортировка устойчива.

## На что обратить внимание при разборе

**Слияние во временный массив.** Сливать в тот же массив, откуда читаем, нельзя:
ещё не прочитанные записи будут затёрты. Временный массив статический — он размером
с весь журнал.

**Устойчивость.** В слиянии стоит нестрогое сравнение: при равном времени первой идёт
запись из левой половины. Со строгим сравнением сортировка останется верной,
но перестанет быть устойчивой.

**Поиск, у которого может не быть ответа в массиве.** Искомого момента в журнале
обычно нет, а ответ всё равно существует — номер первой записи не раньше. Если таких
записей нет вовсе, возвращается число записей, и вызывающий код это проверяет.

**Середина без переполнения.** `low + (high - low) / 2` вместо `(low + high) / 2`.

**Глубина рекурсии.** 15 на 10000 записей и около 20 на миллионе — логарифм,
а не размер массива. Хороший контраст с заливкой в растровом редакторе и обходом карты
в подземелье, где глубина равна размеру области.

**Слияние без побочных эффектов в индексах.** Запись `buffer[k++] = records[i++]`
короче, но два изменения счётчиков в одном выражении читаются хуже; в эталоне
каждый счётчик увеличивается отдельной инструкцией.
