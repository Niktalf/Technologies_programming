# Анализатор логов — практика 12

Продолжение проекта одиннадцатой практики. Источники записей и отчёты
стали двумя иерархиями классов с абстрактными `LogSource` и `LogReport`.
Программа строит любой отчёт по любому источнику, не зная их конкретных
типов. Всё, что умел анализатор на практике 11, осталось.

## Что сделано

```
LogSource (абстрактный: next, describe)       LogReport (абстрактный: accept, print, title)
├── BookSource        загруженный журнал       ├── LevelReport    записи по уровням
├── TextFileSource    текстовый файл           ├── ModuleReport   модули, самые частые первыми
├── BinaryFileSource  двоичный файл            └── HourReport     распределение по часам
├── MultiFileSource   несколько источников подряд
└── RandomSource      случайные записи, как у gen
```

**Источник.** Отдаёт записи по одной: `next()` возвращает
`std::unique_ptr<LogRecord>`, пустой — записи кончились.

- Текстовый источник сам пропускает пустые и испорченные строки.
- Двоичный читает файл по одной записи. Если файл оборван, бросает
  `LogError`, а не заканчивает молча: иначе отчёт выглядел бы полным,
  хотя он неполный.

**Источник из нескольких файлов** построен композицией. Он является
источником — поэтому наследует `LogSource`. И содержит источники — поэтому
хранит `std::vector<std::unique_ptr<LogSource>>`. В нём могут быть
и текстовые, и двоичные файлы вперемешку.

**Отчёт** накапливает записи (`accept`) и печатает итог (`print`). Сам
файлы не открывает. Класс `LogStats` практики 11 разобран на три отчёта.

**Главный цикл** — `run_reports(source, reports)`. Он берёт записи из
источника, пока они есть, и подаёт каждую всем отчётам. Конкретных типов
в нём нет, только два виртуальных вызова.

**Команда `report <что> from <источник>`.** Что: `levels`, `modules`,
`hours` или `all`, можно несколько. Источник: `book`, `file <путь>`,
`files <путь> ...` или `random <число> [зерно]`. Вид файла определяется
по сигнатуре: `LOGB` — двоичный, иначе текстовый. Команды `stats`, `hours`
и `modules` стали тем же циклом по загруженному журналу.

**Где перечислены виды.** Отчёты — только в `make_report`, источники —
в `Shell::make_source` и `open_file_source`.

**Сопутствующие изменения:**

- `LogParser::parse_line` теперь возвращает `std::unique_ptr<LogRecord>`
  вместо добавления в вектор. «Запись или ничего» нужна и источникам.
- `LogGenerator::make_record` — одна случайная запись. Её берут и `gen`,
  и `RandomSource`, поэтому `random 200 2` даёт те же записи, что файл
  `gen b.log 200 2`.
- `BinaryLog` открыл шаги чтения `read_header` и `read_record` для
  двоичного источника.

## Сборка и запуск

```
cmake -S . -B build
cmake --build build
./build/logan sample.log
> report all from book
> gen a.log 300 1
> bsave a.bin
> report levels hours from files a.log sample.log a.bin
> report modules from random 500 2
```

Компилятор GCC или Clang собирает проект с `-Wall -Wextra -pedantic`
без предупреждений.

## Проверка

Отчёт по уровням один и тот же для `book`, для текстового `a.log` и для
двоичного `a.bin`: 85 / 115 / 47 / 44 / 9. Цепочка
`files a.log b.log sample.log a.bin` дала 1000 записей — это 300 + 200 +
200 + 300 — и описание всех четырёх источников:

```
Records: 1000, source: 4 sources: [text a.log, lines read 300, broken 0] [text b.log, lines read 200, broken 0] [text sample.log, lines read 205, broken 4] [binary a.bin]
```

`random 200 2` совпал с отчётом по файлу, записанному `gen b.log 200 2`.
Обрезанный двоичный файл даёт `Error: the data is corrupted`, отсутствующий
файл в середине `files` — `cannot open the file`.

Сценарий из пятидесяти команд практики 11 дал тот же вывод, кроме порядка
строк `modules`: теперь модули идут по убыванию числа записей. Файлы `gen`
и `bsave` совпадают байт в байт. Всё прогнано под санитайзерами адресов,
неопределённого поведения и утечек — без ошибок.

## На что обратить внимание при разборе

**Один цикл, два виртуальных вызова.** `source.next()` и
`report->accept(*record)` — весь `run_reports`. Добавить источник или отчёт
можно, не трогая цикл.

**Композиция против наследования.** `MultiFileSource` является источником
и содержит источники. Наследовать его от `TextFileSource` было бы ошибкой:
он не один файл, а несколько. Тот же приём — паттерн «Компоновщик»
на практике 30.

**Отчёт не открывает файлы.** Отчёт, который читает файл сам, не построить
по генератору или по загруженному журналу. Поэтому записи ему подают.

**Виртуальный деструктор.** Источники удаляются через
`unique_ptr<LogSource>`. Без `virtual` у `~LogSource` деструктор поля
`reader_` текстового источника не выполнился бы, и файл остался бы
открытым.

**Срезка.** Источники в `MultiFileSource` лежат по указателям.
`std::vector<LogSource>` не соберётся: класс абстрактный. А будь он
обычным, от текстового источника осталась бы только база, без файла.

**Инвариант записи окупается.** `HourReport::accept` берёт
`by_hour_[hour]` без проверки: время записи всегда действительно
(практика 11). На практике 11 `LogStats` ещё проверял `hour < 24`.

**Ассоциация.** `BookSource` хранит ссылку на журнал и не владеет им:
журнал должен жить дольше источника. В оболочке так и есть — источник
живёт на время одной команды.

## Язык вывода

Всё, что программа печатает, — на английском: сообщения, подсказки, справка.
Комментарии в коде — на русском. Так вывод читается в любой консоли,
в том числе в консоли Windows, где кириллица в UTF-8 без настройки
превращается в нечитаемые символы.
